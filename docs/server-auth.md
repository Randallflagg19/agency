# Серверная авторизация

Реализованы login/me/logout. Активный администратор `tapir` создан в PostgreSQL
на VPS; публичной регистрации нет. API запускается локально на Mac.
Форма входа, guard, interceptor, запись дел и публикация API ещё не реализованы.

## Как устроена сессия

При входе Argon2id проверяет введённый пароль по хешу из БД. Сам пароль
не записывается в SQL, логи, cookie или localStorage.
После успешной проверки сервер создаёт токен из 32 случайных байт.
Браузер получает его в HttpOnly-cookie, PostgreSQL хранит SHA-256-хеш токена,
ID пользователя и сроки действия. Токен не содержит сведений о пользователе.

`GET /api/auth/me` вызывает `Auth.requireSession`: сервер хеширует токен
из cookie, ищет сессию и проверяет срок и активность пользователя.
Публичный `GET /api/cases` не проверяет сессию.
Для будущих защищённых маршрутов используется `Auth.requireAdmin`: он проверяет
сессию (401 при отсутствии) и роль (403 при недостаточных правах).
Аутентификация определяет личность, проверка роли — разрешённые действия.
Guard в Angular не заменяет эти серверные проверки.

Сессия действует **8 часов с момента входа**, без продления при использовании.
Закрытие вкладки её не отзывает. Истёкшая сессия отклоняется, даже пока её
запись остаётся в БД. API удаляет истёкшие записи при запуске и раз в час.
PostgreSQL сам по сроку их не удаляет.
Logout удаляет текущую сессию сразу и очищает cookie. Повторный вход создаёт
новый токен и отзывает прежнюю сессию этого браузера; другие сессии сохраняются.

## Контракт API

| Запрос | Успех | Ошибки |
| --- | --- | --- |
| `POST /api/auth/login` | 200, `{ user: { id, login, role } }` и Set-Cookie | 400 неверный формат; 401 неверные учётные данные; 403 CSRF; 413 слишком большое тело; 415 неподходящий Content-Type; 429 лимит; 503 сбой сервиса |
| `GET /api/auth/me` | 200, `{ user: { id, login, role } }` | 401 отсутствующая, истёкшая, отозванная или некорректная сессия, а также отключённый пользователь; 503 сбой сервиса |
| `POST /api/auth/logout` | 200, `{ ok: true }` и удаление cookie | 403 CSRF; 503 при ошибке отзыва в БД |
| `GET /api/cases` | 200, массив дел, без обязательного входа | 503 сбой сервиса |

Login принимает JSON `{ "login": "tapir", "password": "…" }`.
У логина убираются пробелы по краям, буквы приводятся к нижнему регистру.
Максимальный размер тела — 4096 байт, пароль при входе — до 128 символов.
Неверный пароль, неизвестный и отключённый пользователь дают одинаковый ответ
401. Для неизвестного логина тоже выполняется Argon2id-проверка с синтетическим
хешем. Ответы не содержат хеша пароля и имеют `Cache-Control: no-store`.
Повторный logout без сессии возвращает 200. При ошибке отзыва в БД — 503,
cookie не очищается.

## Cookie и окружения

| Настройка | На Mac | При публикации на VPS |
| --- | --- | --- |
| `NODE_ENV` | `development` (по умолчанию) | обязательно `production` |
| `APP_ORIGIN` | `http://localhost:4200` (по умолчанию) | точный `https://ваш-домен` |
| Cookie | `agency_session` | `__Host-agency_session` |
| Атрибуты | HttpOnly, SameSite=Lax, Path=/, Max-Age=28800 | те же плюс Secure |
| PostgreSQL | `127.0.0.1:15432`, SSH-туннель | `127.0.0.1:5432` |

`APP_ORIGIN` задаётся без пути и завершающего `/`. В production сервер
не запускается без явного HTTPS-origin. Development допускает только HTTP
на loopback. Domain не задаётся; production-префикс `__Host-` требует Secure
и Path=/. При удалении cookie сохраняются её имя, Path и защитные атрибуты.

Браузер обращается к относительным `/api/...` на origin Angular.
`proxy.conf.json` пересылает их на `127.0.0.1:3000`.
Используйте `http://localhost:4200/`: `127.0.0.1` — другой origin,
для него нужно изменить `APP_ORIGIN`.

При публикации HTTPS должен завершаться на reverse proxy, который обслуживает
сайт и `/api` на одном origin. API слушает только `127.0.0.1`, CORS не разрешается.
PostgreSQL остаётся на localhost; открывать его в интернет не нужно.

## CSRF и ограничение попыток

Для каждого изменяющего запроса, включая login/logout, обязательны:

- `Origin`, точно равный `APP_ORIGIN`;
- пользовательский заголовок `X-Agency-CSRF: 1`;
- для login — `Content-Type: application/json`.

Отсутствующий, чужой или `null` Origin отклоняется. Если присутствует
`Sec-Fetch-Site`, допускается только `same-origin`. Значение `1` не секрет и
не является токеном сессии. Защита основана на том, что браузер контролирует
Origin, а чужой сайт для отправки нестандартного заголовка должен пройти
CORS-preflight. Сервер CORS не разрешает. SameSite дополняет эти проверки.
Это вариант защиты для API, описанный в
[рекомендациях OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html#employing-custom-request-headers-for-ajaxapi).
Будущий interceptor должен добавлять заголовок только к изменяющим `/api`
запросам; встроенный Angular XSRF-механизм сам его не добавит.

Лимит — 10 запросов входа за фиксированное окно 15 минут на весь процесс API,
включая успешные и невалидные запросы после проверки CSRF. Далее — 429 с
`Retry-After`. Одновременно обрабатываются не более двух запросов входа на
процесс. Счётчик и время окончания окна хранятся в памяти.

Лимит общий для всех адресов и логинов и сбрасывается при перезапуске API.
Реализация рассчитана на один процесс.

## Проверки

На Mac:

```bash
pnpm test:server
pnpm exec tsc -p server/tsconfig.json
```

`passwords.test.ts` проверяет Argon2id, случайную соль, верный и неверный пароль,
нормализацию и формат логина. Автоматических тестов HTTP-маршрутов и БД
в текущем наборе нет. Проверка входа с настоящим паролем, me, выхода и cookie
в браузере предстоит после подключения формы.

## Где смотреть cookie в DevTools

После подключения формы входа откройте `http://localhost:4200/` и DevTools:

1. В **Network** выберите запрос `/api/auth/login`. В **Response Headers**
   смотрите `Set-Cookie`: это инструкция сервера браузеру сохранить cookie.
2. В **Application → Cookies → http://localhost:4200** смотрите имя, HttpOnly,
   SameSite, Path и срок действия. HttpOnly-cookie видна в DevTools, хотя
   JavaScript страницы не может читать её через `document.cookie`.
3. У следующего запроса `/api/auth/me` в **Request Headers** смотрите `Cookie`.
   Браузер добавляет её сам для подходящих адреса, пути и срока; Angular
   передаёт относительный URL, читать токен вручную не требуется.
4. У `/api/auth/logout` ответ содержит `Set-Cookie` с `Max-Age=0`.
   Следующий `me` должен вернуть 401. Даже повторная отправка сохранённого
   старого токена не поможет: серверной записи больше нет.

Не публикуйте тело login, Cookie или Set-Cookie: они содержат секреты.
