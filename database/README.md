# PostgreSQL — «Бюро аномальных происшествий»

## Подготовленное окружение

По выводу команд, выполненных пользователем на VPS:

- Ubuntu 24.04, PostgreSQL 16.15, кластер `16/main`, порт `5432`.
- Запуск через `postgresql@16-main.service`.
- `listen_addresses = localhost`; локальный TCP-вход — `scram-sha-256`.
- База `agency_db`, владелец `agency_owner`, UTF8, создана из `template0`.
- `agency_owner`: NOLOGIN, без административных полномочий.
- `agency_app`: LOGIN, NOINHERIT, без административных полномочий.
  Пароль задан пользователем через `\password`, в репозитории не хранится.
- У PUBLIC отозваны все права на `agency_db` и её схему `public`.
- Схема `agency` принадлежит `agency_owner`.
- У `agency_app` есть CONNECT к базе и USAGE на схему `agency`.

Существующие базы и роли других проектов не изменялись.

## Миграции

`migrations/001_create_case_tables.sql` применена на VPS: пользователь передал
успешный вывод выполнения с завершающим `COMMIT`. По последующему выводу
проверены запись в журнале, четыре таблицы с владельцем `agency_owner` и права:
`agency_app` имеет SELECT только на три таблицы данных, без INSERT/UPDATE/DELETE
и без SELECT на журнал. В журнале: `2026-10-25 05:59:11.259381+00`.

Запускать файлы через `psql -X -v ON_ERROR_STOP=1 -d agency_db` от администратора
PostgreSQL. Внутри миграции используется `SET LOCAL ROLE agency_owner`, поэтому
владельцем таблиц становится `agency_owner`.

Миграция выполняется одной транзакцией. Её версия записывается в
`agency.schema_migrations` в той же транзакции. Повторный запуск уже применённой
миграции намеренно завершается ошибкой уникальности версии и ничего не меняет.
Миграция не предназначена для исправления вручную созданных таблиц.

## Структура

- `agency.cases`: поля `IncidentCase` в snake_case. ID и номер — текст,
  номер уникален. Статус, категория и уровень угрозы ограничены CHECK.
- `agency.case_tags`: теги с порядком элементов исходного массива.
- `agency.case_relations`: направленные ссылки с порядком элементов массива;
  оба ID проверяются внешними ключами. Обратная ссылка хранится отдельно,
  если она есть в исходных данных. Ссылка на себя запрещена.
- `agency.schema_migrations`: журнал применённых миграций.

Все три поля location равны NULL, если location отсутствует. Если объект есть,
его description обязателен; region и address могут быть NULL независимо.
`assignee_id` пока не связан с таблицей сотрудников: такой модели ещё нет.
Пустые массивы тегов и связей представлены отсутствием дочерних строк.

`registered_at` хранит момент времени как `timestamptz`: исходное смещение
часового пояса не сохраняется, но момент времени сохраняется точно.
`cover_image_url` хранит путь или URL, а не содержимое изображения.

Миграция предоставляет `agency_app` только SELECT на три таблицы данных.
Права записи для будущих форм нужно будет добавить отдельной миграцией.

## Первичная подготовка на новом сервере

Только после обследования нового сервера и проверки свободных имён, от
администратора PostgreSQL, через `psql -X -v ON_ERROR_STOP=1`:

1. `bootstrap/001_roles.sql` (подключение к `postgres`).
2. `bootstrap/002_database.sql` (подключение к `postgres`; файл переключается
   на созданную базу).
3. `migrations/001_create_case_tables.sql` (подключение к `agency_db`).
4. `seeds/001_mock_cases.sql` (подключение к `agency_db`), если нужны тестовые данные.
5. В интерактивном psql: `\password agency_app`.

Эти bootstrap-файлы фиксируют уже выполненные вручную команды, а не новые
изменения для текущего VPS. Повторно на текущем VPS их запускать не нужно.
Занятое имя роли или базы останавливает подготовку. Создание базы выполняется
отдельно от транзакции настройки прав: при ошибке настройки нужно обследовать
новую базу и завершить настройку, а не автоматически удалять её.

Пароли не хранить в репозитории и не передавать в чат.

## Тестовые данные

`seeds/001_mock_cases.sql` — зафиксированный снимок актуального `cases.mock.ts`:
шесть дел, четыре направленные связи, ноль тегов. Первый запуск на VPS
подтверждён выводом пользователя: вставлены 6 дел и 4 связи, транзакция завершена
с `COMMIT`. Повторный запуск также подтверждён: `inserted_cases = 0`, обе вставки
`INSERT 0 0`, завершение `COMMIT`. Проверки внутри заполнения подтвердили
совпадение полей дел, пустых тегов и исходящих связей со снимком.
Отдельная проверка чтения с правами `agency_app` подтверждена: 6 дел,
4 связи, 0 тегов; номера, статусы, категории и уровни угрозы соответствуют мокам.
Проверен также вход по TCP на `127.0.0.1:5432` с паролем:
`current_user = agency_app`, `current_database() = agency_db`, количество дел — 6.
Поля снимка сверены с исходными моками при генерации.

Запуск: `sudo -u postgres psql -X -v ON_ERROR_STOP=1 -d agency_db < файл.sql`.
Файл предназначен для существующей структуры миграции 001.

Заполнение выполняется одной транзакцией от `agency_owner`. Оно вставляет
только отсутствующие дела и их исходящие связи. Уже существующие дела из снимка
должны полностью совпадать по полям, тегам и исходящим связям; иначе весь запуск
завершится ошибкой без изменений. Совпадающие дела пропускаются. Конфликт номера
с другим ID также откатывает транзакцию. Нет UPDATE, DELETE или TRUNCATE.
Посторонние дела не меняются. Повторный успешный запуск выводит `inserted_cases = 0`.

На время заполнения блокируются другие записи в три таблицы, чтение остаётся
доступным. Это исключает изменение проверяемых данных между проверкой и вставкой.
Теги в этом снимке пусты: файл не вставляет строки в `case_tags`.

## Резервная копия

На VPS пользователь создал `~/agency-backups/agency-initial.dump`
через `pg_dump --format=custom --dbname=agency_db` от `postgres`.
Каталог закрыт правами 700, файл создавался с umask 077.
По оглавлению архив создан `2026-10-25 06:04:57 UTC`, PostgreSQL 16.15.
`pg_restore --list` успешно прочитал оглавление: схема, четыре таблицы,
данные, индексы, ограничения, внешние ключи и права присутствуют.
Фактическое восстановление проверено в отдельной базе `agency_restore_check`:
восстановление прошло без ошибок; чтение с правами `agency_app` показало
6 дел, 4 связи, 0 тегов, исходные номера и названия дел. Журнал содержит
`001_create_case_tables` с исходной датой применения.
Проверочная база оставлена на VPS; у PUBLIC отозваны все права на неё,
самостоятельный CONNECT для `agency_app` не выдавался. Удаление не выполнялось.

Архив одной базы не создаёт роли кластера и не сохраняет их пароли.
При восстановлении на новом сервере сначала нужны роли `agency_owner`
и `agency_app`, затем отдельная база с нужным владельцем и правами CONNECT.
Файлы изображений также не входят в эту копию: в таблицах хранятся их пути.

### Следующие копии

На VPS, в обычной оболочке пользователя `tapir` (каждый архив — новый файл):

```bash
(
  umask 077
  set -C
  agency_backup_file="$HOME/agency-backups/agency-$(date -u +%Y%m%dT%H%M%SZ).dump"
  sudo -u postgres pg_dump --format=custom --dbname=agency_db > "$agency_backup_file" &&
    pg_restore --list "$agency_backup_file"
)
```

При ошибке pg_dump файл может остаться неполным — такую копию нельзя считать
успешной. `set -C` запрещает перезаписывать существующий файл. Оглавление
проверяет читаемость архива, но не заменяет пробного восстановления.
Планировщик резервного копирования в рамках этой задачи не настраивался.

Для копии вне VPS, на Mac:

```bash
mkdir -p ~/Backups/agency
chmod 700 ~/Backups/agency
scp cutesnipe:agency-backups/agency-initial.dump ~/Backups/agency/
chmod 600 ~/Backups/agency/agency-initial.dump
```

Перенос на Mac подтверждён выводом пользователя: файл `~/Backups/agency/agency-initial.dump`
передан полностью (22 KB); выполнены команды установки прав 700 на каталог
и 600 на файл. Для следующих копий подставлять их имена.
Архивы содержат данные проекта: хранить их вне Git в закрытом каталоге.

### Проверенное пробное восстановление

Использовать новое свободное имя базы. Ниже записаны уже выполненные команды;
на текущем VPS повторять создание `agency_restore_check` не нужно.

```bash
sudo -u postgres createdb --owner=agency_owner --template=template0 \
  --encoding=UTF8 agency_restore_check
sudo -u postgres psql -X -v ON_ERROR_STOP=1 -d postgres \
  -c 'REVOKE ALL PRIVILEGES ON DATABASE agency_restore_check FROM PUBLIC;'
sudo -u postgres pg_restore --dbname=agency_restore_check \
  --single-transaction --exit-on-error < ~/agency-backups/agency-initial.dump
```

На другом сервере сначала создать роли из `bootstrap/001_roles.sql`.
Не создавать таблицы и схему миграцией перед восстановлением: они есть в архиве.
После восстановления рабочей базы явно настроить её права: отозвать права
PUBLIC на базу и выдать CONNECT только нужной роли приложения. Права самой базы
этот архив без `--create` не восстанавливает. Пароль роли задать через `\password`.
Перед переключением API проверить данные и права в восстановленной базе.

## Будущий серверный API

Для API на том же VPS:

| Параметр | Значение |
| --- | --- |
| Хост | `127.0.0.1` |
| Порт | `5432` |
| База | `agency_db` |
| Пользователь | `agency_app` |
| Схема | `agency` |
| Пароль | Из защищённых серверных настроек, вне Git и Angular |

Использовать полные имена таблиц (`agency.cases` и т. д.) и параметризованные
запросы. Текущего SELECT достаточно для архива; перед реализацией форм нужны
отдельная миграция прав записи и серверная валидация. Подключать API от
`postgres` или `agency_owner` не следует.

API должен преобразовывать snake_case в поля `IncidentCase`, собирать location
или null, теги и relatedCaseIds в массивы с сортировкой по position. При отсутствии
строк возвращать пустой массив, а не null. Даты возвращать в ISO 8601 с часовым
поясом, например UTC с `Z`. Значения статусов и категорий остаются как в модели.
Пути изображений обслуживает приложение; PostgreSQL хранит только строки.

API, зависимости для него и подключение Angular к серверу не создавались.

## Ручное подключение с Mac через SSH-туннель

В отдельном локальном терминале:

```bash
ssh -N -o ExitOnForwardFailure=yes \
  -L 127.0.0.1:15432:127.0.0.1:5432 cutesnipe
```

Пока терминал открыт, в клиенте БД использовать `127.0.0.1`, порт `15432`,
базу `agency_db`, пользователя `agency_app`. Пароль вводить в клиенте.
Если установлен psql, в другом терминале:

```bash
psql -X -h 127.0.0.1 -p 15432 -U agency_app -d agency_db -W
```

Туннель закрывается через Ctrl+C. Эти команды пока не проверены пользователем.
Сетевые настройки PostgreSQL не менялись; он слушает только localhost.
